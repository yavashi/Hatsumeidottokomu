# 発明ドットコム SDD (Spec-Driven Development) ガイド

本ディレクトリは、Google Antigravityが推奨する **仕様駆動開発 (Spec-Driven Development: SDD)** の中核となるドキュメント群です。  
チャットの一時的な会話に頼らず、リポジトリ内のMarkdownファイルを「唯一の真実の源 (SSOT)」として管理することで、AIエージェントのコンテキスト喪失やハルシネーションを防ぎ、確実な開発を進めます。

---

## 1. ディレクトリ構成

```text
specs/
├── README.md               # 本ガイド（運用の手引き）
├── constitution.md         # プロジェクト憲章（設計原則・技術スタック・品質基準）
├── tasks.md                # タスク管理・進捗状況
├── features/               # 機能別の詳細仕様書
│   └── 01_core_platform.md # コア機能仕様書
└── archive/                # 廃止・大幅刷新された旧仕様の保管庫
```

---

## 2. SDDの基本サイクル

```mermaid
flowchart TD
    A[ユーザーのアイデア・思いつき] --> B[仕様定義 / 差分更新 (Specify)]
    B --> C[技術計画 & 影響調査 (Plan)]
    C --> D[タスク分割 (Tasks)]
    D --> E[コード実装 (Implement)]
    E --> F[検証 & テスト (Verify)]
    F --> G[仕様書とコードの同期 (Sync)]
```

1. **Specify (仕様定義)**: 「何を作るか」「なぜ作るか」を明確にし、`specs/features/` に記載。
2. **Plan (計画)**: 技術的なアプローチ、型定義、コンポーネント構成を設計。
3. **Tasks (タスク化)**: チェック可能な具体的作業に分解し、`specs/tasks.md` に登録。
4. **Implement (実装)**: 仕様に基づきコードを変更。
5. **Verify (検証)**: `npm run lint` や `npm run build`、画面プレビューで検証。
6. **Sync (同期)**: 仕様書とタスクの状態を最新化。

---

## 3. 「思いつき」「頻繁な仕様変更」への対応プロトコル

本プロジェクトは仕様が頻繁に変わることを前提としています。  
思いつきで新しい機能を作りたくなったり、既存の仕様をガラッと変えたくなった場合は、以下のルールで対応します。

### ユーザー側の指示例
- 「〇〇画面のデザインをガラッと変えて、カード形式じゃなくてタイムライン形式にしたい」
- 「思いつきなんだけど、発明家にチップ（投げ銭）を送れる機能を追加したい」
- 「やっぱり〇〇の機能はいらないから削除して、代わりに△△にして」

### エージェント（AI）側の動作
1. **仕様差分先行 (Spec First)**:
   いきなりコードを書き換えず、まず関連する仕様書（`specs/features/`）を更新し、何が追加・変更・廃止されるかを整理します。
2. **デッドコード・旧仕様のクリーンアップ**:
   不要になった機能や古いモックデータは躊躇なく削除・整理し、コードが肥大化したり矛盾したりするのを防ぎます。
3. **高速フィードバック**:
   小さな思いつきであれば即座に仕様・タスク・実装を一気通貫で更新し、実行時検証（ビルド・リント）を行って報告します。
